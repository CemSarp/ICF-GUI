# V3 implementation report — ICF Control Center 0.3.0

*Date: 2026-10-17 · Branch `v3-workflows` (not committed) · Status: **implemented and tested offline;
not yet verified on ICF.** V3 is not marked complete until the approved live smoke test passes.*

## 1. Implementation summary

V3 extends the V1/V2 app without replacing any of it:

- **Remote projects** — bounded, symlink-safe browsing of the remote home, explicit folder creation,
  recent projects and per-project preferences (interpreter, toolchain) stored locally per profile+user.
- **VS Code** — detection from app bundles (works when launched from Finder), Remote - SSH check, an
  `ssh -G` check of what VS Code will see, argv-only launch with a clean environment, a suggested (never
  written) `~/.ssh/config` block, and an optional previewed/backed-up `.vscode/settings.json` change.
- **Python environments** — on-request, non-recursive discovery with a metadata-only probe, configurable
  CUDA toolchain profiles (university CUDA 12.8 preconfigured, existence checked), static CUDA build
  comparison, and a real GPU check as a short SLURM job.
- **Transfers** — SFTP over the existing master (no second login), single queue, SHA-256 verification
  on both ends, resume, cancel, never overwriting, folder packing to `.tar.gz`, bandwidth cap.
- **Training workflows** — a typed configuration rendered into one reviewed wrapper job (submitted
  through the unchanged V2 `jobs_submit`), compute-node scratch staging with a validating archive
  stager, Hugging Face cache policies, checkpoint policies with periodic sync, verified result
  copy-back, signal handling and safe cleanup; batch notebooks and a GPU smoke test.
- **Monitoring** — runs survive restarts (`runs.json`), state reconciled with SLURM plus stage markers
  from a small status file, failure classification, truthful recovery notes, logs, metrics, outputs and
  checkpoints with download/resume.

## 2. Architecture changes

| Area | Change |
|---|---|
| `jobs/request.rs` | `validate()` split into `validate_resources()` + program checks (V2 behaviour unchanged) so workflows reuse the resource rules |
| `jobs/remote.rs` | `Precheck` list + `submit_script_with()`; guarded `make_dir`; `heredoc_safe()` |
| `jobs/commands.rs` | `StoredPreview.workflow`; `jobs_submit` validates workflow previews with `workflow::plan`, uses their prechecks, records the run before/after `sbatch`; refuses scripts that could close their own heredoc |
| `ssh/session.rs` | `Session::sftp_command()` (same ssh, same generated config, ControlPath, BatchMode) |
| `commands.rs` | `AppState` gains project/run/transfer stores, VS Code cache, settings previews, workflow rate-limit cache; disconnect clears V3 in-memory state |
| New modules | `projects/`, `integrations/vscode.rs`, `transfers/` (+ CommonCrypto SHA-256), `workflow/` |
| Capabilities | V3 reads in `default.json`; new `file-mutations.json` for every command that writes a file; workflow submission stays in `job-mutations.json` |
| Dependencies | `tauri-plugin-dialog` (Rust-side native dialogs, no webview permission); `serde_json/preserve_order` (keep settings.json key order). No other new crates; SHA-256 uses macOS CommonCrypto |
| Frontend | `features/projects` (ProjectsView, RemoteBrowser/PickRemote), `features/training` (TrainingWizard, RunsView, TrainingView), `features/transfers` (TransfersView); Settings sections; types/api/format extended |

Diagrams: `docs/ARCHITECTURE.md`. Decisions: ADR-014 … ADR-023 in `docs/DECISIONS.md`.

## 6. Security review findings

Reviewed: credential handling, Keychain, host keys, remote execution, injection, traversal, symlinks,
archive extraction, deletion, overwrites, temp files, Jupyter, port forwarding, logs, concurrency.

| # | Finding | Severity | Resolution |
|---|---|---|---|
| 1 | Publishing an upload trusted a directory validated in an earlier command | Low (same-user race) | publish script re-resolves the directory on ICF and checks it is inside home |
| 2 | Upload progress polled the remote size every 3 s | Low (cluster load) | 5 s; one `wc -c` over the existing master |
| 3 | Opening a run folder in VS Code added it to recent projects | Low (confusing state) | only explicit project opens are recorded |
| 4 | Local file tokens survived disconnect / identity switch | Low | cleared on disconnect |
| 5 | Zip members without file-type bits were rejected as "unsupported" | Functional | type bits checked only when present (found by tests) |
| 6 | `.sr-only` labels could extend the page height | UI | `.main` is a positioned container (found in visual check) |
| 7 | SFTP channel refusal would read as "connection lost" | UX | distinguished when the master is still alive (found by the real sftp test) |

No passwords or tokens are handled by any V3 code path; VS Code receives a cleared environment (tested);
nothing V3 writes to disk contains secrets (tested on `projects.json`, `runs.json`). Host-key checking is
unchanged. No remote daemons, background services or Jupyter servers are created.

## 7. Known limitations

- **Live ICF behaviour is unverified** for: `/disk/scratch` on GPU nodes, `--signal=B:USR1@…`, GNU `find
  -printf`/`timeout`/`sha256sum` on hastings, the SFTP subsystem, the university toolchain path today,
  nbconvert in your env. The smoke test below covers most of these.
- Paths used by jobs, sftp and `#SBATCH` lines are restricted to `[A-Za-z0-9/._+-@=,]`; folders/files with
  spaces can be browsed but not used as projects, transfer destinations or download sources.
- Upload verification runs `sha256sum` once on the login node (nice'd); very large files take a while.
- `df` free space may exceed your `/home` quota; quota errors surface as failed writes.
- If your program ignores SIGTERM it is killed halfway through the copy-back grace period; very large
  outputs may need a longer grace. Nothing is recoverable from a failed node except synced checkpoints.
- Disk-full on scratch during training is detected only via logs (classified as *Scratch / disk full*).
- Multi-node jobs are not supported (single node, as in V2).
- Reconnecting after a dropped SSH session is user-initiated (by design: no automatic re-authentication).
- Interactive Jupyter is disabled (ADR-022).
- The cancel test from V2 is still open.

## 8. Manual cluster verification (needs your explicit approval)

Everything below changes state on ICF and therefore needs your go-ahead. It is sized to be cheap:
**one 10-minute job, 1 GPU of the smallest type, 2 CPUs, 8 GB RAM, plus two small files.**

Preparation on this Mac (no cluster contact): build the tiny dataset archive with
`python3 examples/workflow-smoke/make_dataset.py` (see `examples/workflow-smoke/README.md` for the
full, still small, test table: training, checkpoint sync, resume, failure, unsafe archive, notebook).

In the app, connected to ICF:

1. **Project accessibility** — Projects → browse `~/projects`, *New folder…* `icfcc-smoke`
   (creates one folder), *Open as project*.
2. **Python environment discovery** — *Discover interpreters*, add `~/projects/icf-env/bin/python`, *Use*
   it; choose the university CUDA 12.8 toolchain and check that it shows *exists on ICF*.
3. **Upload** — *New training workflow…* → *Upload an archive from this Mac…* → `tiny_dataset.tar.gz`
   (creates `~/projects/icfcc-smoke/data/` and uploads one small verified file).
4. **Submit** — type *GPU smoke test*; partition Teaching, smallest GPU type, 1 GPU, 2 CPUs, 8 GB,
   0 h 10 m; *Review workflow* → check the script → acknowledge → *Submit workflow…* → confirm.
5. **Watch** — Training → Runs: Queued → Node allocated → Staging data → Training → Copying results →
   Completed; the node, GPU model and Python version appear.
6. **Result synchronisation** — the run's *Outputs* tab lists `smoke.json`; *Results: Copied back and
   verified*; the standard output log contains `@@icfcc-smoke {… "cuda_available": true, "matmul_ok": true …}`.
7. **Result retrieval** — *Download* `smoke.json` to the Mac.
8. **VS Code** — on the project page, *Open in VS Code*; VS Code should open
   `~/projects/icfcc-smoke` over Remote - SSH (it may ask for your password).

Expected: job exits 0, `smoke.json` reports the GPU, the scratch folder is gone (`CLEANED` marker), and
nothing was written outside `~/projects/icfcc-smoke`. Cleanup afterwards is yours to decide (the app
does not delete project folders).
